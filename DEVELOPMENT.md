# Development

This is the contributor dev guide. For the system design, read
[ARCHITECTURE.md](ARCHITECTURE.md). For the contribution workflow (branches,
PRs, gates), read [CONTRIBUTING.md](CONTRIBUTING.md).

## Stack

| Layer | Tooling |
|---|---|
| Backend | Python 3.13+, [uv](https://docs.astral.sh/uv/), Pydantic 2.13+, anyio 4.13+ |
| Browser | [Playwright](https://playwright.dev/python/) (headful Chromium) |
| MCP | `mcp` 1.x (stdio server) |
| Page extraction | scrapling (pinned `==0.4.8`, isolated for swap-out — see [README](README.md#dependencies--risk)) |
| Overlay frontend | Bun, Vite, Svelte 5 (customElement mode, shadow DOM), TypeScript |

## Setup

```bash
git clone <repo-url> frontprompt
cd frontprompt

bash setup.sh                    # one-shot: uv deps + chromium + bun + frontend + overlay build
```

Or manually:

```bash
uv sync                                          # python deps incl. playwright + mcp
uv run python -m playwright install chromium     # if chromium isn't already installed
uv run python -m frontprompt.build               # build + embed the overlay (see below)
```

## The overlay build pipeline

The overlay frontend is built and **embedded into the Python package** at build
time, so the installed tool needs no Bun or Node at runtime. The canonical build
command is:

```bash
uv run python -m frontprompt.build      # codegen → vite → embed into src/frontprompt/_overlay/
```

The `uv run` prefix is required — a bare `python` won't resolve the package.

The pipeline runs three stages:

1. **codegen** — regenerate the TypeScript types in `frontend/src/_generated/`
   from the Pydantic source of truth. Never hand-write a TS type that has a
   Pydantic counterpart; the generator owns those.
2. **vite** — build the Svelte customElement overlay to an IIFE bundle under
   `frontend/dist/`.
3. **embed** — copy the bundle and a manifest into `src/frontprompt/_overlay/`
   so the wheel is self-contained.

To package a distributable wheel with the frontend already inside:

```bash
uv run python -m frontprompt.build --wheel    # build + embed, then uv build --wheel → dist/*.whl
```

Both `_generated/` and `_overlay/` are gitignored build artifacts — never commit
them. They are regenerated by the build.

## Running it

```bash
uv run frontprompt show https://example.com     # open a page with the overlay
uv run frontprompt daemon                        # MCP stdio server (spawns the browser lazily)
```

## Tests, types, lint

```bash
uv run pytest -v                  # python: browser + overlay + bridge + state
cd frontend && bun run test       # frontend (vitest — NOT bare `bun test`, which ignores the vitest config)
cd frontend && bun run check      # svelte-check / type-check the frontend
uv run mypy src/frontprompt       # python type-check
uv run ruff check src tests       # lint
uv run ruff format --check src tests
```

Real-Chromium integration tests live under `tests/browser/`.

## Dev-time state is disposable

The persisted state DB at `~/.local/state/frontprompt/state.db` (picks, regions,
relations) is throwaway dev data while you are developing frontprompt itself.
Clearing it — backing up and emptying the tables, or deleting the file and
restarting the daemon — is fine and expected, e.g. to get a clean slate.

> This applies only while developing frontprompt. For real end-user use these
> are user-authored annotations and must not be deleted without consent.

### State-DB path overrides

`state_db_path()` (in `src/frontprompt/state/persistence/paths.py`) resolves the
SQLite DB in this order — first match wins:

| Env var | Effect |
|---|---|
| `FRONTPROMPT_STATE_DB` | full path to the `state.db` file (most explicit) |
| `FRONTPROMPT_STATE_DIR` | **preferred** — a directory; `state.db` is derived under it |
| `XDG_STATE_HOME` | `$XDG_STATE_HOME/frontprompt/state.db` |
| _(none set)_ | `~/.local/state/frontprompt/state.db` (default) |

The test suite's autouse `_isolate_state_db` fixture (top-level
`tests/conftest.py`) points `FRONTPROMPT_STATE_DIR` at a per-run temp directory
for the whole session, so no test — including browser/overlay integration tests
that spawn `frontprompt show` subprocesses — ever touches your real DB. The
spawned child inherits the variable via `os.environ`.

## Conventions

- **Pydantic is the source of truth.** TypeScript mirrors are generated, never
  hand-written. Keep the drift gate green (see [CONTRIBUTING.md](CONTRIBUTING.md)).
- **Respect the state classification.** Durable, user-authored state is backend
  state; ephemeral page state is local state. See
  [ARCHITECTURE.md § State classification](ARCHITECTURE.md#state-classification-local-vs-backend).
- **One namespace.** Only `window.__fp` — anything else fails the architecture
  tests.
